# One requirement and publication approval

Use this contract for requirement state v5. The interview produces a complete unapproved document. The user reviews that document and the proposed remote operations together. Two machine records may describe one consent; they are not two user confirmations. For v2-v4 recovery, retain the original schema and use the legacy branch in [the shared item cycle](new-issue.md).

## Prepare a concrete preview

Keep the canonical `feature.md` or `bug.md` in the run root and prepare the proposed creation attributes from verified metadata: project, tracker, selected open version as `fixed_version_id`, initial status, existing category ID or null, and Feature Sequencing when applicable. The helper supplies subject and full functional description from the document. It never contacts Redmine or reads credentials.

Prepare a new immutable plan file under `.flow/publications/<operation-uuid>/` before asking for approval. The full preview shows:

- the complete requirement, including scope boundaries and acceptance;
- classification, category, convention, title and other creation choices, with their evidence and rationale;
- the exact initial creation description and the final publication description;
- the named operations and any native relations, including their direction and endpoints;
- the returned-ID binding, preservation of outside human content, and preservation of current issue status.

For a normal new Feature, from the repository root:

```sh
python <project-flow-skill>/scripts/publication_plan.py prepare <state.json> --attributes <creation-attributes.json> --canonical-path 'docs/harness/features/{{created_issue_id}}-<slug>/feature.md' --reviewer <name> --output <plan.json>
```

Use the Bug path for a Bug. The only unknown substitution is `{{created_issue_id}}`, explicitly shown in the final path and target. Creation itself has no unknown fields: it already contains the complete functional sections and immutable run marker. The separately listed description update adds the definitive canonical path after creation. This is one approval cycle with two explicitly authorized operations, not an interview placeholder followed by a newly authorized requirement.

For an issue already created by this run, pass `--before <fresh-issue.json>` instead of `--attributes`, with its known canonical path. The resulting plan has `create: null` and cannot authorize another creation. A relation list, when needed, is passed with `--relations <relations.json>`:

```json
[
  {
    "key": "blocks:foundation:approval",
    "payload": {"issue_id": 100, "issue_to_id": "{{created_issue_id}}", "relation_type": "blocks"}
  }
]
```

Use actual known IDs for existing endpoints. The stable key is retained after binding. Do not add unrelated relations or fields. Present the human-readable descriptions and choices, not merely a hash or an abbreviated plan. Keep any ambiguity that prevents a concrete choice open before requesting approval.

**Complete when:** the document passes its Feature/Bug contract, all material choices are concrete, the plan contains the full approved-to-be content and listed operations, and its generated bytes are available for review.

## Record the single consent

After approval, record classification, similarity and category confirmation provenance and the title-convention confirmation. Reuse earlier valid confirmations, especially inherited scope decisions. From the same consent identity and timestamp append:

- `kind: requirement`, whose `subject_sha256` is the canonical document's exact bytes and whose `document_path` points to its immutable snapshot under `.flow/publications/<uuid>/`;
- `kind: publication-plan`, whose `subject_sha256` is the printed plan hash and whose `plan_path` is its item-relative `.flow/publications/<uuid>/plan.json` path.

The plan stores the same reviewer and requirement hash. It is immutable once referenced. Do not silently edit a plan or canonical document covered by approval. Phase completion and operation transitions are persisted separately; the plan can authorize future bindings without pretending an operation has run. `requirement-approved` completes only after the plan and canonical approval validate.

**Complete when:** one consent is attributable, both matching machine records and selection provenance are durable, and state validation accepts the unchanged document and plan.

## Bind and execute each authorized operation

Generate creation payload bytes without another confirmation:

```sh
python <project-flow-skill>/scripts/publication_plan.py bind <state.json> --approval-id <plan-approval-id> --operation create --output <create-payload.json>
```

Persist `remote_operations.create` with `status: approved`, the returned `payload_sha256`, `plan_approval_id`, and the plan consent's `approved_by`/`approved_at`. Verify remote context and execute only that operation. Persist its outcome and issue ID before moving the run or advancing `item-created`. A recorded ID or completed creation prohibits another create.

For publication, retain a sanitized fresh snapshot under the operation directory. It must have the same issue ID and subject; its managed section must match the preview's recorded baseline. A different managed section is a material divergence to resolve. The helper preserves fresh outside human text byte-for-byte, even if added after the original preview:

```sh
python <project-flow-skill>/scripts/publication_plan.py bind <state.json> --approval-id <plan-approval-id> --operation publish --before <fresh-issue.json> --output <publish-payload.json>
```

Persist the approved publish operation with the returned hash, plan consent and `plan_approval_id`, plus item-relative `baseline_path` and exact `baseline_sha256`. Retain that baseline and payload for recovery. The validator derives the same payload from the approved plan, persisted ID and frozen baseline. The update contains `issue_id`, `changes.description`, and the selected `changes.fixed_version_id`; run the publication checker after readback.

For a relation, use its listed stable key as `--operation`. Preserve that key and the bound endpoints in state. Check for an existing equivalent native relation before calling create. Record matched existing relations as reconciled without inventing a mutation attempt. The current state contract requires an attempt for a completed creation/publication, not for an already-existing relation.

**Complete when:** every executed operation has a matching bound fingerprint and plan consent, each outcome is durable before the next operation, and final projection plus state validation pass.

## Changes and retries

A known failure retains the same payload and approval. An uncertain outcome must be reconciled with remote evidence before retrying or changing the operation; never infer failure from silence. A matching remote effect completes locally, proven absence permits the unchanged retry, and an ambiguous or divergent result blocks mutation.

For a material change, prepare the delta in `.work/`, retaining the previous approved bytes while review is pending. Do not execute affected operations during this review. Show the changed requirement and affected operation payloads; approval of that concrete delta produces a new full immutable plan and matching canonical approval, and invalidates the superseded records. Keep all old plans and consent records. A payload revision is possible only while the operation is `approved` and has no attempt or its latest attempt is a known failure. Append the previous operation snapshot (without nested `revisions`) to `revisions`, preserve attempt history, then bind the new authorized payload. Unknown and completed operations cannot be revised this way.

A changed fresh baseline that only adds outside human content can be rebound under the same plan's preservation rule before any attempt; retain the previous operation snapshot and both baselines. This does not alter approved functional content or authorize overwriting human edits. Once an outcome is unknown, reconcile the exact previously bound payload first.

Completed operations stay immutable. For changes after completed publication, use the separate explicitly requested alignment/review workflow and preserve historical closure. Legacy v2-v4 operation fingerprints remain immutable under their existing transition rules.

**Complete when:** unchanged retries reuse their consent, material changes have an approved delta, prior evidence/history survives, and no unknown outcome or duplicate creation is bypassed.
