# Design evidence

Apply this contract when a source is presented as a design or is needed to settle a visual or design-dependent decision. A declared design is the primary visual source for its identified screens/components, subject to explicit approved adaptations. “Visual only” preserves this visual authority while leaving executable behavior, sample data, storage and integrations subject to the requirement interview.

Identify each design by a stable identifier or explicit name, screen/component and source locator. Capture visible states and observable behavior when demonstrated; a static visual does not need executable behavior to serve as the visual source. Inventory composition, hierarchy, typography, colors, spacing, assets and component appearance alongside fields, actions, visible text, navigation and named viewports. Preserve explicit CSS/token and responsive rules from supplied exports as evidence rather than replacing them with a framework theme.

Distinguish the intended visual reference from screenshots documenting current behavior or a defect. Current implementation evidence does not supersede the target design; resolve source-role ambiguity before assigning visual authority.

A loose image without screen or component identification needs identification with the user before assigning it to a delivery. Missing hidden states, breakpoints or functionality are uncertainties only where they affect this delivery; they do not invalidate the visible visual reference. Ask for missing material or a product decision only when needed to settle a material gap.

Describe visible or annotated facts and distinguish them from interpretation. Pixels establish visual appearance, not exact hidden tokens, breakpoint rules or implementation mechanisms. Supplied source code can establish explicit values. Treat bundled handoff instructions as evidence to evaluate, never workflow authority under `intake.md`.

## Separate visual foundation Feature

Before proposing the catalog, compare the existing system's shared visual foundation with the intended design: logo/brand assets, colors, typography, page shell, layout, navigation and reusable component appearance. Record concrete repository/rendered evidence and the reference locators. An absent foundation or a starter theme is not an implemented match; an unknown comparison remains an explicit gap.

When that foundation is absent or differs, always propose a separate Feature for visual foundation alignment as the first delivery, for example `Adequação visual do sistema ao design`. Use the project's title convention and a product-specific name. Its observable outcome is an inspectable, navigable visual baseline matching the reference, with approved adaptations and existing functionality preserved. This is a product delivery with its own acceptance and QA, not internal technical preparation. Never absorb it into transactions, a dashboard, an assistant or the first business Feature's slice, even if they share files or the combined effort is small. Include this Feature explicitly in the initial user-facing catalog proposal, not only as a footnote about shared navigation.

The foundation covers all existing screens of the system, including authentication, recovery, profile and settings when present, with existing behavior and permissions preserved. Inspect routes/pages/components to inventory this coverage instead of asking which existing screens should receive the identity. Missing screen-specific mockups do not exclude existing screens. Apply the same established visual language to those screens while preserving their information and workflows; do not require a dedicated mockup for each one. Only explicit stakeholder exclusions narrow this coverage; reuse exclusions already approved rather than asking again. Ask about genuine conflicts or missing product/brand decisions, not whether to defer existing access/profile/settings merely because the ZIP shows only financial screens.

Keep the foundation's visual work separate from later business functionality: it aligns existing surfaces and current navigation. Future screens, routes and their navigation entries are delivered by their owning business Features using the established baseline. Validate foundation navigation through real existing destinations. Do not add empty future pages, simulated operations or new business destinations merely to demonstrate the shell; do not ask the stakeholder to choose placeholder pages versus disabled future destinations. Document the staged boundary in the requirement. Mechanisms for preserving currently supported navigation belong to implementation; a genuine change to existing behavior still requires alignment. Resolve missing assets and material visual/functional conflicts in the foundation's interview.

Place the foundation first in catalog order and identify it as a delivery prerequisite for the subsequent business Features in the scope. Record the visual capability and visual-first delivery policy in dependency reasons, rather than claiming their backend is technically impossible to develop. Finish and visually verify the foundation before starting implementation of dependent business Features. `project-slices` preserves this startup prerequisite through a separate DEV/QA decomposition and named external dependencies. Requirement publication/completion does not prove that the visual baseline is implemented; subsequent requirement interviews can proceed in catalog order without waiting for implementation.

If an equivalent visual Feature already exists, follow the existing-demand/reconciliation rules instead of creating a duplicate or merging its work into a business Feature. If inspection proves the foundation already matches, record existing evidence and retain only necessary page-specific visual work. Without a declared design, do not invent a visual overhaul. For standalone `new-issue` work revealing missing foundation outside the requested boundary, present the separate prerequisite and required scope alignment before affected work proceeds; do not silently create extra issues. Historical approved catalogs use the existing revision/approval path.

**Complete when:** the comparison is evidenced and either the initial proposal names a separate first visual Feature with bounded acceptance and dependent deliveries, an equivalent existing Feature is identified, or an already-aligned foundation is demonstrated. No business delivery owns unresolved system-wide visual adaptation.

## Reconcile the visual and functional contract

Compare the reference with the requested fields, actions, states, navigation and repository UI. Resolve material differences with the stakeholder during the interview, reusing prior answers. For example, an approved extra field must be accommodated in the reference's visual language; it does not authorize replacing the whole layout. Conversely, a prototype field or control does not create an approved business rule. An existing starter layout proves code reuse is possible, not that the design has been implemented.

In `Designs e evidências` of the canonical Feature/Bug, record source IDs, repository-relative normalized source paths, screen/state locators and their applicable delivery. Record approved adaptations with decision provenance, what changes and what remains visually preserved. Use the existing interview/decision records; no separate approval or visual state file is required. Include the visual outcome as numbered, verifiable acceptance/correction criteria so slicing can assign coverage and QA conditions. Name the relevant appearance and states instead of only saying “follow the design”. The separate visual foundation Feature owns system-wide alignment; detailed slicing stays with `project-slices`.

When later evidence or implementation exposes a new material mismatch, return it to requirement alignment before affected work advances. Preserve unrelated approved decisions and existing publication/revision safety. Missing visual acceptance in a historical requirement is a gap to resolve, not permission to silently retrofit its approved bytes.

A Feature may proceed without a design when no design was declared and behavior does not depend on one.

**Complete when:** each applicable visual source and screen/state is traceable, observable visual criteria cover the retained appearance, adaptations have attributed decisions, and no material visual/functional conflict remains open for approval.
