# Ralph execution

Run:

```sh
bash <plan-issue>/ralph.sh execute <dev-directory>/planning.md
```

Ralph reads phases and the suite command directly from `planning.md`. It creates `.flow/ralph-state.json` beside the plan, containing current phase/gate, completed phases/commits and an operational `current_execution_id`. The UUID selects the persistent private phase ledger; it is not approval proof. Deleting state deliberately starts a new execution identity and forgets progress without undoing commits or changes. Ordinary resumes must preserve it.

Before starting gates, the executor validates the plan's `Referências visuais` section under [the planning contract](planning-contract.md). Its declared normalized source files are included in required reading for development, correction and validation. Missing sections/sources and unsafe paths stop execution without changing progress. Historical plans need an explicitly reviewed amendment; the workflow never erases resume state to introduce visual criteria.

Gate 3 selects its interpreter from the baseline fence according to [the contract](planning-contract.md), including on Windows, without interactive profiles. A missing interpreter, invalid Bash syntax, Bash exit 126/127 and cmd exit 9009 stop execution as operational failures, preserving changes and state without returning to development in that run. Other nonzero exits receive read-only diagnosis before routing to correction, controlled investigation or interruption. Internal scripts of tools such as Composer may use another shell; check portability when preparing the baseline.

## Per-phase gates

Retain the Portuguese stage names in user-facing updates:

1. **Desenvolvimento:** opens a fresh Codex session to implement only the phase, without committing.
2. **Validação:** opens another fresh read-only session to review requirement, diff, tests, security, standards and applicable visual acceptance against the primary design and approved adaptations.
3. **Testes:** the script directly runs the complete suite declared in the baseline.
4. **Commit:** the script runs `git commit --no-verify` and moves to the next phase.

Demonstrated defects return to focused Development correction. An observed required behavior with an unknown cause goes to focused Development investigation, which may inspect/instrument application code, tests, fixtures and process-local configuration. Root cause is an outcome, not a prerequisite for investigating. Neither route authorizes scope changes, weaker assertions, new dependencies or global permission changes. Only positively established external prerequisites/scope decisions, protocol/safety violations or exhausted intervention limits stop execution.

Missing captures for an existing state use `kind: evidence-missing`, separately from environmental `verification-blocked`. Each missing-evidence finding quotes the governing phase/shared plan excerpt in `plan_basis`; the executor checks that the quote exists in the approved scope and stops on an invalid request. The reviewer must justify the requested coverage, including any full viewport/theme product. Scope ambiguity stops for alignment; it never authorizes more implementation or an invented capture matrix. Historical results without the new kind retain their conservative blocked behavior.

When only missing captures remain, Ralph saves a sanitized evidence request in the task's Git runtime and runs the already approved capture command once more with `RALPH_EVIDENCE_REQUEST` pointing to it. The console announces **Evidências**; no development session starts and no test/commit gate runs until independent validation approves. The next review receives both original and supplementary reports/images. The JSON is diagnostic data, not a new approval manifest or an executable command. The capture command must implement the requested fixture/coverage under [the capture contract](planning-contract.md).

One supplemental capture/review is allowed per validation attempt. A remaining in-scope fixture/evidence gap with `blocker_condition: none` can enter bounded Development investigation; missing approved commands, confirmed prerequisites or legacy untyped gaps save `evidence-blocked`, preserving the request and code. Rerunning the same command feeds that request to capture before review, without repeating development. Interrupted `evidence-preparation` also resumes at validation. Environmental blockers stop rather than trigger evidence preparation; mixed findings prioritize demonstrated defects before bounded investigation or a confirmed blocker. Evidence completion cannot synthesize application changes or modify the approved plan.

Validation results include `visual_validation` with status `verified`, `not-applicable` or `blocked` and evidence/reason. Findings distinguish `kind: defect` from `kind: verification-blocked`. A mixed verdict corrects demonstrated defects first. An in-scope unresolved behavior with `blocker_condition: none` and a verified `plan_basis` can enter focused Development investigation; evidenced external/scope blockers save `current_gate: validation-blocked` before tests/commit. Resuming the same command then regenerates evidence and returns directly to validation. Legacy custom results with untyped findings and blocked visual verification stop conservatively rather than guessing a code defect. A blocked comparison or nonempty findings cannot accompany approval. Gate 3 passing does not supersede missing Gate 2 visual evidence.

When the approved phase contains `### Verificação renderizada`, Ralph runs its single command on the parent host before review, exporting `RALPH_EVIDENCE_DIR` and `RALPH_PHASE_NUMBER`. Each attempt gets fresh private artifacts/logs under `.git/ralph-runtime`; the command must produce actual captures and preserve repository source. The reviewer receives this report and inspects the images without launching a browser or writing temporary files inside its read-only sandbox. A failed command cannot be silently approved, but its output can establish an actionable application defect. Source modifications by capture or validation interrupt execution and are preserved for inspection. No agent receives broader sandbox permissions.

Existing UI plans without a capture command need a reviewed amendment when accessible current evidence is missing. Do not delete resume state, erase changes or approve static inspection as visual acceptance. Runtime artifacts are diagnostic evidence; no new approval manifest or state hash is introduced.

Development returns a complete report with `checks` and labelled `visual_evidence` (path, reference, screen, state, viewport and theme). Ralph saves the sanitized report under the task's Git runtime directory and injects it in full into validation, including when resuming a blocked or interrupted validation session. Corrections replace that report. Historical runs without a saved report explicitly report its absence; accessible evidence can still be inspected. The local `.flow` state remains minimal. Evidence is input to independent comparison, never an inherited approval.

When a handoff report is too large for inline input, the prompt names its complete UTF-8 file in private runtime storage. Read that file in parts and follow its artifact mappings; the reference preserves the full report and does not replace inspection or grant approval.

Development/correction returns `status: completed` only after implementation, or `status: blocked` when an environment/access/scope obstacle prevents completion. A blocked report supplies the concrete reason in `summary`, nonempty diagnostic `checks` and preserved partial files. Ralph saves the full sanitized report before checking status or Git changes, stops in `development-blocked`, and shows the cause and report path without opening validation/tests/commit. Runtime/protocol failures also stop at that stage. A completed implementation/correction result without repository changes still fails its gate, but now retains and displays the agent's explanation. Rerun the same command after fixing the obstacle: preflight runs again, followed by development with partial work preserved. The environmental reason is not sent as a focused code correction; demonstrated defects retain their ordinary correction flow.

The parent preflight report is included in both development and correction prompts. A completed parent check establishes readiness for implementation; the agent may inspect its existing log/images and proceeds without relaunching preflight inside its sandbox. The parent supplies capture variables only to the capture subprocess; their absence in a model session is expected. A `CAPTURE_OK` line is a project script's diagnostic, not an additional marker to obtain inside each agent. New implementation obstacles return a blocked development result. Preflight images still do not demonstrate acceptance of the implementation that follows.

When code, tests and capture support are implemented and only sandbox-limited check execution remains, development/correction returns `ready-for-host-checks` with nonempty `pending_checks`: `host` maps to the approved phase `Verificação no host`, `rendered` to `Verificação renderizada`. Completed/blocked results use an empty array; legacy custom results without it retain their existing interpretation. The console reports implementation ready with checks pending. The parent opens a **Verificações no host** stage before validation, using only the approved commands; it never executes a command from the result JSON or guesses readiness from a blocked summary. Missing implementation/test/fixture logic remains development-blocked. Required undeclared commands require plan amendment.

Every declared host command runs after development/correction, even for an ordinary completed result, with source-change protection and isolated `TEMP`/`TMP`/`TMPDIR`. Capture-specific variables are not inherited by this command. It must use check-only modes, isolated test data and cleanup of owned processes. Rendered checks retain their existing evidence environment. Their completed images/report feed validation without an immediate duplicate capture. The full sanitized host report is saved under the task Git runtime and supplied to independent review alongside development and rendered evidence. Host success is verification input, not code approval.

For an executed host/rendered command returning a normal nonzero result, Ralph opens **Diagnóstico**, a fresh read-only `diagnose-host` session. It receives failed reports, context and the private failure registry. Its dedicated schema selects `correction`, `development-investigation` or `blocked` per observed failure, never phase approval. A block needs affirmative external/scope evidence and a supported `blocker_condition`; `none` routes unknown causes to investigation. Unverified phase/standard quotations restrict work to investigation rather than granting correction authority. Unsafe standard paths stop.

Proven defects return to `correct.md`; unknown causes use `investigate-development.md` in the Development workspace-write role. Both receive only selected failure groups, relevant interventions and preserved report paths. Preserve correct work and approved scope; after work the normal mandatory checks run again. Mixed findings handle known defects before remaining investigations/blockers. Every verification and model report retains its own private evidence file.

Confirmed external/scope blockers, invalid/approved diagnosis, startup failures, missing declared commands or unsafe source changes stop before approval/tests/commit. Unknown cause alone, unchanged files and exhausted old stage history do not establish a blocker. Startup/timeouts and source-changing verifiers remain operational/safety stops. Repair and rerun the same command with work/state intact. Host-stage resumes repeat approved host checks; validation resumes require saved successful host proof. Historical development-blocked tasks still need an explicit ready/completed report. Custom runners must implement the new diagnosis schema or retain conservative legacy blocking.

The executor assigns a UUID to each observable failure group, using approved criterion, behavior, expected result and assertion references. Variants such as themes/viewports can share a group; unrelated behavior in the same file or stage cannot inherit its quota. Supported associations reuse identities across host, rendered checks, review and Testes. Unverified claimed associations are preserved as provisional separate observations, bounded by the phase-wide cap. Legacy stage histories remain evidence only.

A Development investigation must supply verifiable new findings (`cause-established`) or actual instrumentation/fixture changes (`evidence-prepared`). Evidence preparation requires source progress beyond generated outputs. Static established findings are retriaged before deciding the next focused action. An identical no-progress intervention is not automatically repeated. When instrumentation needs execution, the parent may run one approved reproduction per failure: a focused reproduction is eligible only if its declared `Caso` references and `Esperado` expectations cover the selected group. Otherwise use the failed approved verifier. Model JSON never supplies shell commands. Normal artifact protection/timeouts apply.

Default limits are **six Development interventions per phase including initial implementation**, and **two focused interventions per failure**, configurable by `--max-attempts` and `--max-failure-attempts`. Reserve before opening a worker; interruptions consume the reservation. A batch counts once globally and once for each selected group. Private ledger counters survive source changes, corrections and resumes; neither a new handoff nor an edit replenishes them. Legacy migration counts a valid saved implementation once and does not transfer old stage quotas. Initialization happens once per phase execution UUID. Private ledgers/reference reports retain observations, changes, outcomes and artifact mappings without enlarging approval state.

Gate 3 uses the same triage and focused Development policy. After investigation/correction, approved host/rendered checks, independent acceptance and the complete suite still run before commit. A diagnostic reproduction that passes is evidence, not approval, proof of a fix or confirmed flakiness. No recovered direct-green path bypasses review or commits a phase. Confirmed external suite failures save `tests-blocked`; resuming retains counters/history and returns through independent review and the required suite.

An approved `### Preflight da validação` command exercises the real bootstrap/browser/authenticated fixture and writes a protected-screen capture before development and again on resume, under the same parent capture environment. Failure saves `preflight-blocked` before development or retains `validation-blocked` on review resume, preserving source changes. Repairing the environment and rerunning continues at the appropriate stage. Plans without the section do not perform this check; prepare it under [the capture contract](planning-contract.md) before claiming readiness. Authentication must be recreated independently or replaced by durable, labelled rendered evidence; closing development's browser must not invalidate review.

The executor defaults to `gpt-6.1-sol` for development and validation gates. Choose another model with `ralph.sh execute <planning.md> --model <model>`. The default runner fixes reasoning effort at `medium` in both gates, overriding Codex CLI configuration for those runs. The executor does not access Redmine or YouTrack and uses no subagents. Its default backend requires Codex CLI; `RALPH_AGENT_COMMAND_JSON` may provide another compatible runner as a JSON argument array, and the chosen model is available as `RALPH_MODEL`. This backend dependency is separate from the `ralph` skill, which can be operated through Codex, Claude Code or OpenCode.

Before opening a model session, the default runner probes the selected `CODEX_BIN`/PATH executable with `codex exec --help` and checks its advertised model/config/sandbox/structured-output flags and the required role mode. Missing options, startup errors and probe timeout produce an explicit compatibility/configuration diagnostic without launching a model or falling back to broader permissions. This checks the CLI interface, not whether an effective sandbox implementation is available. Windows implementation selection remains with the user's/administrator's configuration; Ralph does not force MXC, clone/filter `config.toml`, disable user configuration or enable network access. Development remains `workspace-write` and review remains `read-only`. Validation startup/protocol failures save the same blocked stage for direct validation resume.

Each parent-side capture receives a separately owned short-lived temporary directory through process-local `TEMP`, `TMP` and `TMPDIR`. The parent environment and global settings remain unchanged. Browser profiles/build temporaries are cleaned after the command, including failures; capture scripts must still close their own processes. Images and sanitized logs belong to the separate persistent `RALPH_EVIDENCE_DIR`, so cleanup does not invalidate evidence returned to the reviewer or later diagnostics.

On Windows, each launched command belongs to a native Job Object whose lifetime ends with its launcher, including remaining descendants after normal exit or cancellation. A validated Development handoff is recorded before collecting generated outputs. If collection fails, the existing host-check resume path preserves that handoff and its intervention count; it does not open another Development session. Sandbox-unavailable investigation checks go directly to the approved host commands.

## Resume and minimal safety

All parent verifiers share one output lifecycle: preflight, host commands, rendered commands and Gate 3 receive a fresh persistent `RALPH_ARTIFACTS_DIR`. Tools can write there directly using their supported output configuration. Fixed workspace output roots belong in `### Artefatos de verificação` under [the planning contract](planning-contract.md); there are no framework-specific directory rules or extension exemptions. The executor archives prior untracked outputs before phase startup/clean-worktree checks and stages verified copies before clearing those roots for each command. Generated outputs are similarly preserved after success, failure, timeout or cancellation, before checking source integrity. Artifact reads/copies use streaming content checks and reject symlinks/junctions/unsafe paths.

Each command's report retains its original status/message/log, artifact mappings and a separate source-guard result. Thus a failed browser assertion with a screenshot, trace or coverage output can reach diagnosis. Source writes, unsafe paths or archive errors still stop, without erasing the underlying assertion/error. Tracked files, including image baselines/metadata in output roots, are never moved or exempted from source checks. Untracked files outside declared outputs remain protected too. Copy failures leave originals; failed removals attempt restoration without overwriting concurrent files. Previous and current same-named outputs have separate archive locations.

Host failure diagnosis and independent review receive durable artifact mappings; original workspace paths may no longer exist. These artifacts explain execution and do not replace required post-development visual acceptance images. Commit stages tracked source normally and excludes only untracked contents of declared output roots, preventing generated diagnostics from entering the phase commit. Commands must still close their owned processes before returning. Unknown output locations require a reviewed plan declaration; Ralph never guesses that every PNG, ZIP, JSON or new directory is disposable.

A task allows only one simultaneous execution. A new phase requires a clean worktree. If a phase attempt already left changes, rerunning the same command resumes that phase from development, except that interrupted or blocked validation resumes directly at validation with the saved handoff. A failed commit with pending changes resumes validation and the complete suite before retrying commit, preserving implementation without reopening development. If execution ended immediately after commit, state at the commit gate with a clean worktree recognizes current `HEAD` as the phase commit and continues.

The `.flow` directory must be Git-ignored. The operational execution UUID and private revision fingerprints track resume identity/progress only; they are not approval manifests, baseline proof or evidence reconciliation. Do not delete them or reset counters to bypass a refusal. The developer remains responsible for reviewing history and deliberately replacing a plan or undoing work.

## Output

The Bash launcher starts Python with `-X utf8`, giving stdout/stderr a UTF-8 default even when redirected on Windows. Unicode diagnostics such as Rector's `✓` must remain printable through rejection and focused correction. This is process-local initialization; it does not change system encoding, gate criteria or saved progress.

By default, the terminal shows only human-readable Portuguese messages:

```text
Fase 1 iniciada
[DESENVOLVIMENTO] Gate 1 em andamento [08:48]
[DESENVOLVIMENTO] Gate 1 finalizado [08:52]
[VALIDAÇÃO] Gate 2 aprovado [08:55]
[TESTES] Gate 3 aprovado [08:58]
[COMMIT] Gate 4 finalizado [08:58]
Fase 1 finalizada
```

Errors show the sanitized cause and diagnostic path. Prompts, stdout, stderr, tests and structured events remain in `.git/ralph-runtime`. Use `--verbose` to display technical events in the terminal.

Agent stdout/stderr are drained concurrently and sanitized line by line into their diagnostic files while the process runs, including before timeout or cancellation. Heartbeats every 30 seconds remain in structured diagnostics and `--verbose`; normal output favors concrete milestones. Partial lines become available when the runner flushes a newline or closes its output.

Development, correction and review prompts request 3–6 meaningful short commentary lines during a long session, starting with `RALPH_PROGRESS:` and naming observed work/results in pt-BR. The executor extracts only explicit marker lines, sanitizes credentials/control codes, bounds each to 180 characters, removes repeated messages and retains the latest pending milestone. It prints the first immediately, at most one per 60 seconds thereafter, and flushes the latest pending line when the process ends. These become `agent-update` events with a reported activity message; they never change a gate's state or constitute verification approval. Ordinary tool transcripts, command text and full prompts stay in private logs. Custom runners can emit these optional lines on stderr without changing final JSON; runners without them retain gate-transition output. No additional model call summarizes logs.

The principal agent consumes these compact messages and gate events rather than repeatedly tailing transcripts. User updates identify current work, completed checks or the next concrete step in a short sentence. Quiet intervals do not justify invented progress or percentages; diagnostics are read only for a specific investigation, with bounded excerpts.

Default timeouts are 60 minutes for development, 30 for validation, 10 for parent-side capture and 60 for tests. Adjust with `--dev-timeout-minutes`, `--validation-timeout-minutes`, `--render-timeout-minutes` and `--tests-timeout-minutes`. Capture owns its declared processes and must clean them up; timeout/cancellation terminates only the subprocess tree started by Ralph.

Host checks default to 10 minutes per command, configurable with `--host-timeout-minutes`; this also applies to a rendered command explicitly deferred to that stage. A normal validation-side capture still uses `--render-timeout-minutes`.
